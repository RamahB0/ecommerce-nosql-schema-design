# Reflection Report

The hardest part of the refactor was resisting the urge to solve analytics by adding more indexes to the operational order store. That approach looks simplest at first, but it directly conflicts with the original throughput requirement: every index and every ad-hoc aggregation query adds write overhead and contention on the exact path that has to sustain thousands of transactions per second. The real fix was accepting a second, purpose-built schema fed asynchronously by change data capture, and getting comfortable with that data being a few minutes stale, a trade I would not have made in Part 1, where every write path served a single, immediate purpose.

The new requirements changed the design more in degree than in kind. Part 1 already picked different consistency models per field (quorum writes for order and payment status, relaxed consistency for catalog browsing); the refactor mostly extended that same instinct outward, choosing shard keys that avoid hotspots, replicating across zones and regions, and, for analytics, choosing to duplicate data rather than query live tables. The main new judgment call was explicitly trading strict consistency for availability wherever correctness didn't strictly require it, since a system serving many more users can no longer treat "briefly unavailable" as harmless.

In terms of outcome, the refactor moves query performance for analytics from an expensive scan competing with checkout traffic to a read from a small, pre-aggregated table, at the cost of a few minutes of staleness. Sharding and multi-region replication remove single points of failure and let both the catalog and the order pipeline keep serving traffic through node or zone failures, at the cost of shard-key and consistency-level decisions that now have to be made deliberately rather than left implicit.
